#### 预期结论： 
1.无压缩会溢出失败  
实测中 no_compression 在第 5 轮左右达到 165,227 tokens，超过演示预算 128K，失败。证明原始网页内容不能无限累积。  

2.压缩能显著提高任务成功率
除无压缩外，其余 5 种策略都成功完成任务。说明压缩是长上下文 Agent 的必要能力。  

3.不同策略有不同取舍，不是压缩越狠越好
context_aware_summary：最省 token，40,157 tokens，压缩比 3.0%，适合成本敏感任务。  
individual：保留页内细节，但最慢，约 2980 秒，token 最高，276,608。  
combined：一次总摘要，较平衡，93,449 tokens，1189 秒。  
citations：最利于追问和溯源，但上下文更大，222,992 tokens，3 次溢出。  
windowed：只压缩旧消息，保留最近全文，字符压缩比约 102.4%，但完成最快，867 秒，适合长多轮任务。  
4.上下文预算需要故意收紧才能观察行为
实验使用 Agnes- flash-2.5，真实窗口约 1M，但把 CONTEXT_WINDOW_SIZE 限制为 128K，目的是让溢出和压缩行为可见。  
5.单次绝对值会波动，相对排序才是重点
实验证明的是策略之间的相对趋势：无压缩失败、上下文感知摘要省 token、逐页摘要慢、窗口化适合长多轮、带引用利于追问。  


## 思考：
- 短期记忆的本质就是每次发给模型的 messages 列表：System Prompt + 对话历史 + 工具调用记录。所谓短期记忆管理，就是管这个列表里“什么进、什么出、什么被压缩”。短期记忆管理的常见手段包括滑动窗口（只保留最近 N 轮对话）、摘要压缩（丢之前先让模型把早期对话压成摘要）以及选择性保留（核心约束和工具关键结果单独存结构化数据）。  
- 长期记忆并非单一实体。从认知科学视角，长期记忆可进一步细分为语义记忆（存储概念性、事实性知识，如领域知识库和规则）和情境记忆（记录具体交互或环境事件的序列和结果，用于复盘和经验学习）。此外还有语境记忆（捕获当前外部环境或对话背景）和元记忆（对自身记忆状态的认知和管理能力，即“关于记忆的记忆”）。  
- 用户记忆系统的构建方式：不保存每句对话，而是用额外的 LLM 调用提取、压缩并审查对未来有用的事实。提取结果需同时满足三条规则：选择性（丢弃短期细节）、抽象化（把本次具体行为归纳为长期偏好）、结构化（用可检索的字段保存事实）。配套项目包括 user-memory（长期用户记忆系统）和 mem0/memobase（开源框架对照实现）。  
- 记忆系统的技术实现形式：记忆的存在形式多种多样：数据库/文件系统用于保存持久化记录和用户档案；向量数据库将文本或多模态信息映射为向量，支持语义相似度快速检索，是语义记忆系统的核心；知识图谱以图结构表示实体及其关系，适用于组织复杂结构化知识；神经网络权重则是内隐记忆，不能在运行时动态增删。  
### RAG 在 Agent 中的作用：
从固定管线到动态工具：

- 标准 RAG 管线的协作方式是固定流程：接受用户查询 → 执行搜索 → 组合上下文 → 调用语言模型。编排器不会决定“是否搜索”“查询哪些索引”或“采取多少检索步骤”——这些决策在设计解决方案时就已确定。

- Agentic RAG 改变了这一模型。AI Agent 将检索视为可随时调用的工具，而非固定流程。Agent 会推理用户查询，决定调用哪些工具，评估中间结果，并反复迭代直到有足够上下文以产生有根据的答案。这种方法能实现多步骤推理、动态查询规划和跨异质数据源的协调。

核心架构：推理与行动的循环：  
- Agentic RAG 的核心是一个自主 Agent 作为编排器，它维护内部记忆、监控任务进展，并决定何时以及如何检索新信息。它可能制定子目标、执行工具，或根据中间结果修订查询。

- 其运作模式可概括为 ReAct（Reasoning + Acting）循环：语言模型充当推理引擎，接收用户查询，检查可用工具，生成函数调用以请求特定数据；Agent 执行该函数并将结果返回给模型；模型决定是继续调用其他工具还是生成最终回应。

- 在 Agentic RAG 中，检索不再是一个静态的预处理步骤，而是嵌入推理循环中的自适应、序列化操作。每次迭代，Agent 都会评估当前知识状态，并决定是否需要用修订后的提示查询检索器、调用外部工具、存储/检索工作记忆，或生成部分/最终输出。关键架构进步在于通过推理进行查询重构——一个过于宽泛的初始查询会被逐步分解为更窄的子查询。

适用场景：何时需要 Agentic RAG：  

- Agentic RAG 并非在所有场景下都优于标准 RAG。当查询足够直接、单次搜索单索引就能解决时，标准 RAG 更合适——因为每个 Agent 推理步骤都会增加延迟、Token 消耗和复杂度。但在以下场景中，Agentic RAG 能带来标准 RAG 无法提供的价值：
  - 多步骤推理：需要从一个来源收集信息，分析后再根据分析查询另一个来源
  - 动态来源选择：在运行时决定查询哪个数据源，而非查询所有来源
  - 查询分解：将复杂问题拆解为后续查询，分别执行后进行比较
  - 反复精炼：第一次检索不够充分时，评估结果、识别缺口，用精炼词汇或筛选器再次查询
  - 操作与检索结合：在同一工作流程中既收集信息又采取行动

RAG 与记忆系统的关系

- RAG 技术与长期记忆紧密相连。用户记忆和知识库共用许多底层技术——向量检索、知识压缩——也面临同样的麻烦：信息冲突、知识过期、检索不准。向量数据库支持语义相似度快速检索，用于 RAG 记忆检索，是当前语义记忆系统的核心。在更宏观的架构中，长期记忆结构因 Agent 而异，许多系统使用基于向量的记忆，配合 RAG 风格的检索，以应对 LLM 上下文窗口的限制。

## 学习心得
- 当控制台有一堆输出时，很难找到关键信息，目前解决办法是把控制台输出发送给ai，分析具体结果。
- 很多时候会出现一些问题导致不能得到理想的结果，但这些问题不会报错，在没有足够的知识积累和经验，应该如何排查问题呢？

  - 不要只说“效果差”。写成：期望指标是多少？容差多少？实际指标是多少？从哪一步开始偏离？最终输出、中间结果、还是评估本身？有没有一个“已知正常”的基线？
  - 无报错时，必须主动看内部。  
  加日志/指标：  
  输入统计：范围、均值、缺失、单位、维度。  
  中间量：每层输出、梯度、残差、能量、损失、条件数。  
  异常哨兵：NaN、Inf、全零、饱和、超范围、不变化。  
  耗时、内存、迭代次数、是否提前停止。  
  - 最小可复现 + 控制变量
    固定随机种子、版本、硬件、配置。  
    用玩具数据或单样本，构造能手算期望结果的小例子。  
    一次只改一个东西，记录结果。  
    从“已知能工作”的配置出发，逐步替换成你的配置，二分找到第一次变坏的点。  
  - 不要盯最终结果。沿流程插检查点：  
    输入 → 预处理 → 模型/算法 → 中间状态 → 后处理 → 评估。  
    找到第一个与参考/预期不一致的中间量，问题通常就在它前一步。  
  - 参数太小的通用排查：如果怀疑参数太小：  
    对数扫描：1e-6, 1e-5, 1e-4 … 1e-1，画响应曲线，找平台、拐点、阈值。  
    看它是否低于某个分支阈值，导致逻辑根本没触发。  
    看它是否被其他项量级支配，等于没生效。  
    看是否导致下溢、舍入、迭代不足、采样不足、收敛容差过早满足。  
    放大 10 倍/100 倍做定性判断：结果变好，说明方向对；不变，可能不是它。  
  - 用参考和断言代替经验  
    对比官方示例、论文代码、同类库、旧版本。  
    对比中间输出，不只对比最终指标。  
    在关键位置加 assert：形状、范围、单位、NaN、梯度范数、残差。  
    检查默认值陷阱：最大迭代、容差、采样数、线程数、缓存、超时、正则系数。  
  - 常见静默问题清单  
    数据：标签错、泄漏、分布偏移、缺失、异常值。  
    数值：单位错、量纲不匹配、整数除法、float32 精度、下溢/上溢。  
    代码：广播、视图/拷贝、索引 0/1、行列主序、异常被吞、缓存。  
    环境：依赖版本、硬件、并行竞争、随机性。  
    评估：指标算错、阈值错、数据划分错。
  - 记录与求助  
    每次实验写：目标、假设、改动、结果、结论。这样经验会自己长出来。  
    求助时给：最小复现、期望、实际、已试方法、日志、环境、版本。别人更容易帮你。  
    一个万能短流程：定义成功指标 → 固定环境 → 最小复现 → 看中间量 → 找第一个异常 → 对标参考 → 参数对数扫描 → 加断言 → 修复后加回归测试。
